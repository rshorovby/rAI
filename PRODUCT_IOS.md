# RallyMind — iOS как второй канал игрока

Документ зафиксирован по итогам architecture grill (2–3 сентября 2026).  
Источник истины для **нативного клиента игрока** и подготовки бэкенда под второй канал.

**Статус:** этап D (identity + сервисный слой на SQLite) — в коде. HTTP / IAP / APNs / iOS v1 — не начаты.

Пайплайн разбора, Forum-кабинет тренера и human-in-the-loop — в [`PRODUCT_V2.md`](PRODUCT_V2.md). При конфликте по очереди ревью приоритет у V2. Этот файл не заменяет V2 и не делает iOS отдельным продуктом.

---

## 1. Решение

iOS — **дополнительный вход того же RallyMind**, не замена Telegram и не новый продукт.

| Роль | Где живёт |
|------|-----------|
| Игрок | Telegram и/или iOS |
| Штатный тренер | только Forum в Telegram |
| Движок | Gemini + очередь ревью + SQLite на текущем Droplet |

Сейчас HTTP-бэкенда нет: есть Telegram-бот. Второй канал садится на **доменный слой** (анализ, квоты, заявки, прогресс), не на Bot API.

---

## 2. Зафиксированные решения grill

| # | Тема | Решение |
|---|------|---------|
| 1 | Роль iOS | Канал игрока того же продукта. Тренер остаётся в Forum. |
| 2 | Идентичность | Внутренний `player_id`. Telegram и Apple — привязки, не первичный ключ. iOS-only допустим. |
| 3 | Слияние аккаунтов | Привязка Telegram → iOS **только в пустой** аккаунт приложения. Две живые истории не мержим. Пустой Telegram к живому iOS — просто привязка id. |
| 4 | Оплата | IAP в приложении + Stars в боте. Entitlement на `player_id`. В iOS нет CTA «плати в Telegram». Покупки видны в обоих каналах. |
| 5 | iOS v1 | Только ядро (см. §4). Профиль, «написать тренеру», practice, follow-up — не в этом релизе. |
| 6 | «Готово» | APNs, если приложение установлено. Если есть `telegram_id` — сообщение в бота как сейчас, откуда бы ни ушло видео. |
| 7 | Видео | Клиент жмёт до лимитов бота (сейчас 20 МБ и длительность тарифа). Object storage нет. Дальше temp → mute → Gemini → Forum → удаление. |
| 8 | Intake | Как в боте: удар → на что смотреть → можно пропустить + опциональный комментарий. |
| 9 | Привязка Telegram | Одноразовый код в боте (`/link`) и в приложении. Оба направления. Telegram Login / Universal Links / ввод username — нет. |
| 10 | История | Заявки и отчёты **без видео на сервере**. Прогресс = scores из `player_sessions`. Локальная копия файла — на устройстве. |
| 11 | Инфраструктура | **Вариант D** (см. §5). Postgres и отдельный API-сервис до iOS — нет. |
| 12 | Контракт отчёта | Markdown + разобранные `scores` / `focus` / `drills` / `stroke`. HTML — только адаптер Telegram (`formatting.py`). |

Онбординг в UI iOS v1 нет, но это отложенный кусок того же продукта. Ручка анализа **уже читает** `player_profiles`, если строка есть (ветеран Telegram после привязки получает тот же контекст, что в боте).

## 3. Умолчания (не гриллили отдельно)

Принимаем, пока явно не отменим:

- вход в iOS — только **Sign in with Apple**; Telegram не является логином;
- из приложения можно **удалить аккаунт** (требование App Store);
- сессия API — непрозрачный токен в SQLite, не JWT-платформа;
- когда появится HTTP — домен, nginx, TLS на том же Droplet.

---

## 4. iOS v1 — состав

### Делаем

- Sign in with Apple
- Привязка Telegram кодом в **пустой** iOS-аккаунт (выгрузка прогресса из бота)
- Загрузка видео (сжатие на клиенте) + intake как в боте
- Статус заявки (очередь / ревью / доставка / fallback)
- Текст отчёта + scores
- История заявок и прогресс (ряды scores, как `/progress` в боте)
- IAP, общий Pro/квота с ботом
- APNs о готовности отчёта

### Не делаем в v1

- Онбординг / редактирование профиля (данные профиля с сервера — да, если уже есть)
- «Написать тренеру»
- Follow-up диалог с Gemini
- Practice-цепочка и напоминания в приложении
- Галерея видео на сервере
- Кабинет тренера в iOS
- Паритет со всем `bot.py`

## 5. Вариант D — готовим код, не базу

Делается **до** HTTP и TestFlight, на живом Telegram-канале.

### Что меняется внутри

1. Таблицы `players` и `identities` (`provider` + `subject` → `player_id`).
2. Миграция: каждый текущий `users.user_id` (Telegram) → `player` + identity `telegram`. Все сущности с `user_id` игрока переходят на `player_id`.
3. Граница бота: `message.from_user.id` → `resolve_or_create_player("telegram", id)` → дальше только `player_id`.
4. Сервисный слой без типов Telegram: анализ, постановка в очередь ревью, квота, доставка отчёта, прогресс. Бот — адаптер (скачать файл, написать в чат, запостить в Forum).
5. SQLite остаётся. Включить WAL. Бэкап: `rally.db` и `-wal`.
6. `COACH_USER_IDS` не трогаем — это Telegram-аккаунты тренеров.

HTTP, IAP, APNs, Apple identity в D **не входят**.

### Что не меняется снаружи

Игрок, тренер, Stars, Forum, fallback 24ч, practice-cron — те же сценарии. D не меняет продуктовый пайплайн V2.

### Зачем, если снаружи ничего не видно

Без D в день iOS придётся одновременно вводить идентичность, HTTP и клиент. D переносит риск на этап, который проверяется текущим ботом и pytest.

Узкое место роста — штатный тренер, Gemini и RAM Droplet на видео, **не SQLite**. Postgres — когда появится второй процесс/машина или измеренные блокировки, не «на всякий случай до канала».

### Риски миграции

- Сбой маппинга id → квота/Stars/тема Forum разъедутся. Деплой только со снимком `data/rally.db`.
- `review_jobs.video_file_id` остаётся Telegram `file_id` для заявок из бота. В сервисе это ссылка канала, не универсальное хранилище. iOS потом кладёт файл в temp и идёт в тот же анализатор; в Forum бот шлёт уже свой `file_id`.
- Cron должен слать в Telegram через identity, а не считать `player_id` chat id.

## 6. Что переиспользуется

| Слой | Вердикт |
|------|---------|
| `analyzer.py`, промпты, wiki, `video_mute.py`, `report_parser.py`, `pricing.py` | Да, как есть |
| Квоты `billing.py`, `review_jobs`, fallback, `player_sessions` / прогресс, профиль | Да, после `player_id` |
| Оркестрация «видео → заявка → отчёт» | После выноса из `bot.py` в сервис |
| `bot.py`, клавиатуры, Stars как оплата iOS, `formatting.py` как канон отчёта, `context.user_data` | Нет |

Пишется с нуля под канал: HTTP, Sign in with Apple, проверка IAP, APNs, коды привязки, multipart, удаление аккаунта, сам клиент.

---

## 7. Порядок работ

```text
1. D на текущем боте (identity + сервис, SQLite)
2. HTTP + IAP + APNs + коды привязки
3. iOS v1 (ядро)
4. Позже: онбординг в приложении, «написать тренеру», practice, follow-up
```

Не начинать iOS и D одним заходом. Не мигрировать на Postgres «чтобы потом было проще добавить канал».

## 8. Связанные инварианты из V2 (не пересматривались)

- Разбор всегда через очередь к человеку; игроку — после send или fallback 24ч.
- Gemini стартует сразу при приёме видео.
- Квота списывается при постановке в очередь.
- Кабинет тренера = супергруппа + Forum Topics.
- Одна тема Forum на игрока (`player_id` после D).
